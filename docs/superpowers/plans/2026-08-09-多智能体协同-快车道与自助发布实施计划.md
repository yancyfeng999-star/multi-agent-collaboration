# 多智能体协同：快车道与 Agent 自助发布实施计划

> **给执行 Agent 的要求：** 必须使用 `superpowers:executing-plans` 按任务逐项执行。默认采用当前会话内的有界执行方式；除非用户明确批准，不创建额外 Agent。

**目标：** 通过一次性 Preflight、明确的快速执行档、有限恢复策略，以及串行的任务/线程自助发布与抢占机制，消除不必要的多 Agent 等待，同时保持 Strict 和 Release 工作流的 fail-closed 安全边界。

**架构：** 继续以 Protocol v3 Document Bus 作为唯一事实源，以 Codex Native 消息作为执行适配层。新增治理模式/执行档路由和只读 Preflight；已获授权的工作 Agent 可以在父任务范围内直接创建、发布和派发子任务，不必唤醒主 Coordinator。所有任务、资源和线程抢占都使用 Run 内锁、不可变记录和范围校验，不能借自助发布绕过发布许可或 Strict 人工/安全门禁。

**技术栈：** Python 3 标准库 CLI、项目现有的扁平 YAML/JSON 协议格式、不可变 Markdown/YAML/JSON 文档、Codex Native/Document 适配器、`unittest`、Git 证据以及现有 Protocol v3 状态回放。

- P0 行为、测试和说明全部通过后，Skill 版本从 `1.3.0` 升级到 `1.4.0`。项目交付版本仍由项目自身的 version contract 管理，不能由 Skill 自动递增。
- 保留现有治理值 `light`、`standard`、`strict`；文档可以使用方案中的 `L`、`S`、`X` 别名，但不强制重命名 CLI。
- `execution_profile: fast` 只减少交接、重复询问和等待，不降低风险等级、不删除 Strict 门禁。
- 不为派发、队列、版本、Release、安全或超时单独创建 Agent；复用 Coordinator、Owner、合并后的 Reviewer/QA 等已有能力。
- 默认编制：Light 一个 Coordinator/Owner；Standard 一个 Owner 加一个独立且合并 Reviewer/QA 的质量 Agent；Strict 只增加项目规则明确要求独立授权的能力。
- 不启动 daemon、不忙轮询、不伪造 ACK/lease/result/review/QA，不把 Native 消息发送成功当成任务完成。
- 自助发布必须满足：发布者有能力、存在父任务、引用父任务 hash、范围属于 Scope Freeze、目标 Agent/claim 合法、没有活动路径冲突，并完成串行写事务。
- 一个任务或一个 Native 线程最多只能有一个有效 Claim。抢占冲突应立即返回可处理的机器结果，不能循环等待或静默抢走。
- 数据库、支付、资金、权限、密钥、生产、migration、部署、Release、回滚等 Strict 边界继续 fail-closed，并由项目适配层提供业务规则。
- 所有新增 CLI 都必须支持 `--dry-run` 和稳定 JSON 输出。退出码约定：`0` 成功/就绪，`2` 存在缺失、冲突或阻断，`3` 协议输入不合法或不安全。

## 1. 现实问题与成功标准

### 1.1 当前问题

当前 Skill 的规则本身是正确的，但链路过长：工作 Agent 遇到门禁后请求 Coordinator 检查，Coordinator 再请求其他 Agent 补字段，Run 重新扫描，随后又发现新的缺口。真正耗时的是串行唤醒、上下文转交和重复排查，而不是写一份协议文件。

当前 `references/modes-and-gates.md`、`scripts/emit_event.py`、`scripts/validate_run.py` 还存在“开始工作后才发现完成证据不足”的情况，导致工作 Agent 不能快速知道下一步到底缺什么。

### 1.2 目标行为

| 场景 | 优化后的行为 | 仍然禁止 |
| --- | --- | --- |
| Light 调研、文档、低风险测试 | 一个 Owner 完成 task/result/summary，不再唤醒 Reviewer/QA | 声称可发布或可进入生产 |
| Standard/fast 代码任务 | 一个 Owner 加一个独立合并质量 Agent；派发前一次列完全部缺口 | 绕过 Review/QA、Owner 自审 |
| Strict 或 Release 任务 | 保留现有 fail-closed 门禁，先一次性列出缺证据 | 自动降级、自动生产发布、伪造证据 |
| Owner 不 ACK、lease 过期 | 在固定时限内生成真实阻断/恢复记录并释放槽位 | 无限 lease、静默改状态、无限重试 |
| 工作 Agent 发现子任务 | 在父任务和冻结范围内直接创建/派发，不必唤醒主 Coordinator | 扩大范围、路径冲突、创建未注册 Agent |
| 多 Agent 抢同一任务/线程 | 串行校验，首个合法 Claim 获胜，其余立即获得 holder/expiry/next action | 两个有效 Owner、静默接管、忙轮询 |
| Native 不可用 | 同一个自助操作生成 Document invocation package | 报告已唤醒或已完成但没有事实文件 |

### 1.3 可量化验收目标

1. 新建 Light/fast Run 只执行一次 Preflight，不需要 Reviewer/QA 交接。
2. Standard/fast Run 用一次 JSON 同时列出全部 dispatch/completion 缺口，每个任务最多一次合并质量交接。
3. 下一次有界 tick 后，过期 lease 不能继续占用并行槽位。
4. 两个并发 Claim 必须只产生一个有效胜者，不能产生重复 owner/lease。
5. 工作 Agent 可以在不唤醒 Coordinator 的情况下发布授权子任务，并完成可验证的事件/操作记录。
6. Strict 和 Release 校验不弱于当前 v3。
7. 候选摘要不能暗示 MG/生产权限，项目 Release adapter 仍是发布裁决者。

## 2. 运行模型

### 2.1 治理等级、执行档与派发策略分离

```text
governance = light | standard | strict       # 风险和证据下限
execution_profile = fast | normal            # 只表示时效偏好
dispatch_policy = central | hybrid | self_service
```

- `central` 保持旧行为。
- `hybrid` 由 Coordinator 负责全局 ready wave，同时允许获授权的工作 Agent 在父范围内发布/派发子任务。
- `self_service` 允许工作 Agent 在相同 Preflight 和事件校验下直接完成派发，不等待 Coordinator tick。
- 新 Light/Standard 默认 `hybrid`；新 Strict 默认 `central`，只有项目适配层明确允许时才启用 `hybrid`。
- 旧 Run 缺字段时按 `normal + central` 解释，不改变旧事件含义。

### 2.2 Mode Router

| 触发条件 | 建议治理 | 建议执行档 |
| --- | --- | --- |
| 调研、计划、文档、内容、独立只读测试 | `light` | `fast` |
| UI、API、脚本、常规代码、本地测试、共享服务 | `standard` | 普通为 `normal`，紧急时为 `fast` |
| 数据库、支付、资金、权限、secret、provider、storage、部署、Release、回滚、生产 | `strict` | `normal` |

多个等级同时命中时取最高等级。Coordinator 可以把模式调高、把执行档改快并记录理由，但不能因为“着急”把高风险任务降级。

### 2.3 最小 Agent 编制

- **Light：** 一个 Agent 可以同时承担 `coordinator`、`owner`、`task_publish`。
- **Standard：** 一个 Owner 加一个独立质量 Agent，质量 Agent 同时承担 Reviewer 和 QA；只有权限或执行环境不能合并时才拆分。
- **Strict：** Coordinator 继续负责版本和门禁；复用 Owner/合并质量 Agent；Security/Data/Release 只在项目规则要求独立边界时增加。
- **自助派发：** 是已有 Agent 的能力，不新增“Dispatcher Agent”。

### 2.4 目标流程

```text
Interview / 风险识别
        ↓
Mode Router → Scope Freeze → 一次性 Preflight
        ↓                         ↓
    ready                  missing/conflict/blocked
        ↓                         ↓
任务图/任务池 ← 机器可读 next_action
        ↓
Coordinator 或工作 Agent 自助发布
        ↓
串行抢任务/抢线程 → ACK / 有界 lease → 工作与证据
        ↓
Completion Preflight
   ┌──────────────┬──────────────────┬────────────────────┐
   │ Light        │ Standard         │ Strict             │
   │ result关闭   │ 合并Review/QA    │ 安全/环境/人工门禁 │
   └──────────────┴──────────────────┴────────────────────┘
        ↓
Candidate Index（只摘要，不授予发布权）
        ↓
项目自己的 Release-Ops adapter 决定目标环境
```

### 2.5 自助协同派发层：不是放开权限，而是增加受控能力

这部分是本次优化的关键。工作 Agent 不再必须通过“唤醒主 Coordinator → Coordinator 再派发”的路径，但也不能直接改任务、改 owner 或绕过门禁。正确做法是把“发布、抢占、唤醒”拆成三个可审计能力，挂在已有 Agent 身上：

```text
task_publish   创建并派发父任务范围内的子任务
task_claim     抢占 claimable 任务
thread_claim   抢占一个可用 Native 线程/执行槽
```

它们不是新的 Agent 角色。一个现有 Owner 是否拥有这些能力，由 Run 的 `dispatch_policy`、Agent Registry、父任务关系和 Scope Freeze 共同决定。

#### A. 工作 Agent 自己发布子任务

工作 Agent 在发现需要下游处理时，直接调用 `agent_dispatch.py publish`，流程固定为：

1. 读取当前父任务、父任务 hash、Run manifest、Scope Freeze、活动 task/lock/claim。
2. 运行一次发布 Preflight，确认发布者有 `task_publish`，父任务处于允许派发的状态，子任务依赖父任务或已完成上游任务。
3. 校验子任务的 `owned_paths` 是父任务/冻结范围的子集，目标 Agent 已注册，Standard/Strict 的 Reviewer/QA 不与 Owner 冲突。
4. 取得 Run 内唯一的 `task-publication` 排他锁，再次读取并校验活动状态；不能只依赖锁外的旧快照。
5. 在同一个短事务中暂存 task、更新 manifest task index、生成 `TASK_READY`/`TASK_DISPATCHED`，并把 `parent_task_id`、`parent_task_sha256`、`publisher_agent` 写入操作记录。
6. 释放文件锁后再调用 Native 或 Document adapter，避免网络/线程等待占用全局锁；Native 失败时写 Document fallback，不重复创建任务。

这样，Coordinator 仍然掌握全局治理、版本、Strict、Release 和恢复权，但不再是每个子任务的必经唤醒通道。

#### B. 抢任务：只允许抢任务池，不允许静默接管固定 Owner

任务增加两种 assignment：

- `fixed`：已有明确 Owner，只能由该 Owner 执行；其他 Agent 即使空闲也不能抢。
- `claimable`：任务 owner 在冻结文档中为 `pool`，并声明 `eligible_agents`；第一个通过串行 Claim 的 Agent 成为本次 attempt 的 effective owner。

抢任务的顺序是：

```text
claim lock
  → 检查任务状态、依赖、eligible_agents、Scope、max_parallel、路径锁
  → 写不可变 task claim
  → 写 TASK_DISPATCHED（causation_id = claim_id）
  → 唤醒目标 Agent 或生成 Document package
```

两个 Agent 同时抢同一任务时只有一个可以写入有效 Claim；另一个得到 `holder_agent`、`lease_expires_at`、`blocked_by` 和 `next_action`，不能循环重试。Claim 到期后，Light/Standard 必须经过 timeout evidence/recovery 才能再次进入队列；Strict 的未知副作用不能自动接管。

#### C. 抢线程：抢执行资源，不抢身份和事实

`thread_claim` 只表示某个 Agent 暂时占用一个已验证的 Native 执行线程/槽位，不改变 Agent 身份，不把聊天消息当成任务完成。Claim 必须绑定：

- `thread_id`、平台和真实 session binding；
- 精确 workspace；
- task claim、task hash 和 lease 区间；
- 对应 Native operation ID。

同一线程只能有一个有效 Claim。线程不可用时，工作 Agent 直接走 Document Bus fallback；不能为了“抢到线程”创建第二个假线程或复用另一个项目 workspace。Strict 线程 Claim 不允许自动静默迁移，必须进入显式恢复。

#### D. 串行和不冲突的锁顺序

为了防止两个 Agent 同时发布或抢资源，所有自助操作使用固定顺序：

```text
Run publication lock
  → task/thread claim lock
  → events/.sequence.lock
  → 按路径排序的 resource locks
  → 写不可变 operation/event/claim
  → 释放锁
  → 调用 Native/Document adapter
```

锁只保护校验和事实写入，不包住外部网络调用。所有路径、逻辑资源和 task bundle 必须一次检查、一次授予，不能部分成功；父子路径视为冲突。任何一项失败都返回 JSON 冲突，不写半个 ready 任务。

#### E. 哪些场景仍必须回到 Coordinator

自助发布只减少不必要的调度往返，不改变治理边界。以下情况仍然必须由 Coordinator 或用户门禁处理：

- 扩大 Scope Freeze、增加未确认的正式交付范围；
- Strict 的 change ID、registry、security、environment、migration、backup、rollback 或 Release gate；
- 修改项目版本合同、创建 RC、改变目标版本或版本权威源；
- `TASK_COMPLETED` 的 Standard/Strict 最终收口、`RELEASE_READY`、dead-letter 和生产恢复；
- 活动 task/lock/claim 状态不确定，或外部副作用状态为 `unknown`；
- 需要创建新的 Agent、提升委派深度或修改用户已确认的权限边界。

因此，“工作 Agent 可以自助发布”与“Coordinator 不再存在”是两件事：前者是受控的执行捷径，后者不会发生。

## 3. 需要先冻结的数据合同

### 3.1 Manifest 新字段

新 Run 的 `manifest.yaml` 和 `assets/manifest.yaml.template` 增加：

```yaml
execution_profile: "fast"
dispatch_policy: "hybrid"
preflight_required: true
scope_freeze_ref: "null"
scope_freeze_ref_sha256: "null"
retry_policy_ref: "<run-dir>/config/retry-policy.yaml"
retry_policy_ref_sha256: "<sha256>"
self_service_parent_scope: "task_owner_or_declared_collaborator"
```

`preflight_required` 对 Strict 永远不能为 false。`retry_policy_ref` 必须指向 Run 内不可变策略快照，不能直接读取全局可变配置。

### 3.2 Task 新字段

`assets/task.md.template` 和 `assets/schemas/task.schema.json` 增加：

```yaml
assignment_mode: "fixed"                 # fixed | claimable
eligible_agents: []                       # claimable 时必填
published_by: "coordinator"
parent_task_id: "null"
parent_task_sha256: "null"
resource_steps: "[]"                     # {step_id, kind, resources}
```

`fixed` 保持现有 owner 规则。`claimable` 任务在冻结文档中使用保留 owner 值 `pool`，真正执行前由不可变 Claim 文档提供 effective owner；没有有效 Claim 时不能 ACK、lease 或写 result。

### 3.3 Preflight JSON 合同

所有 Preflight 都返回统一结构：

```json
{
  "schema_version": "1.0",
  "run_id": "RUN-...",
  "task_ids": ["TASK-001"],
  "governance": "standard",
  "execution_profile": "fast",
  "dispatch_policy": "hybrid",
  "ready": false,
  "missing": [
    {"field": "git_status_ref", "owner": "coordinator", "reason": "standard completion evidence"}
  ],
  "conflicts": [],
  "blocked_by": [],
  "required_actions": ["record accepted git_status evidence before dispatch"],
  "estimated_handoffs": 1,
  "next_action": "record_evidence",
  "checked_at": "<iso8601>"
}
```

报告本身不是事件，也不是 Release 决策；数组必须稳定排序，使 Coordinator 不必反复人工扫描。

### 3.4 Scope Freeze

`decisions/scope-freeze.yaml` 不可修改，至少包含：

- `scope_id`、`run_id`、`objective_sha256`、`created_at`；
- requested/allowed paths 和标准化 forbidden paths；
- 初始化前已经存在、明确排除的 dirty files；
- 已确认的 task/change ID；
- target environment、`max_parallel`、治理等级、执行档和派发策略；
- version contract 和 retry policy hash；
- `owner_agent: coordinator` 和 user confirmation 引用。

任何子任务必须证明自己的路径是该记录的子集。新增范围只能创建新的 task revision 和 human gate，不能静默修改冻结文件。

### 3.5 Retry Policy

Run 内默认策略：

```yaml
ack_timeout_seconds: 600
progress_timeout_seconds: 900
result_timeout_seconds: 600
max_attempts_light: 2
max_attempts_standard: 2
max_attempts_strict: 1
owner_noop_action: "blocked_then_reassign"
auto_retry_light: true
auto_retry_standard: false
auto_retry_strict: false
immutable_events: true
```

项目适配层可以收紧，不能提高 Strict 自动重试次数，也不能把 side-effect `unknown` 当成可以安全重试。

### 3.6 Claim 文档

任务 Claim 放在 `claims/tasks/`，线程 Claim 放在 `claims/threads/`：

```yaml
protocol_version: 3
kind: "task_claim"
claim_id: "CLAIM-..."
run_id: "RUN-..."
task_id: "TASK-..."
task_sha256: "..."
claimer_agent: "A02-owner"
eligible_agents: ["A02-owner", "A03-worker"]
lease_acquired_at: "<iso8601>"
lease_expires_at: "<iso8601>"
parent_causation_id: "<event-or-task-id>"
status: "active"
```

线程版本另外记录 `thread_id`、平台/session binding hash、workspace 和 task claim ID。Claim 文件只新增，不修改。

## 5. 上线与回滚

### 5.1 分阶段上线

1. **只读阶段：** 先上线 Preflight、Completion Preflight、Candidate Index 的 dry-run；旧 Run 仍 central、不改状态。
2. **Light 灰度：** 新建 Light/fast/hybrid 文档或测试 Run，确认一个 Owner、没有 Review/QA 唤醒、一次 Preflight、完整 result/summary。
3. **Standard 灰度：** 本地 UI/API/script 任务使用一个合并质量 Agent，确认 fast 不删除 Review/QA。
4. **自助派发灰度：** 授权工作 Agent 发布一个无冲突子任务，抢一个任务和一个线程，执行双进程竞争测试。
5. **超时灰度：** 使用故意缺 ACK/过期 lease 的 fixture，确认 BLOCKED/recovery 有界且旧事件不变。
6. **Strict shadow：** 只对本地 Strict fixture 做 Preflight/Candidate Index，不连接 MG、成都、生产、真实凭据、支付或外部 provider。
7. **默认启用：** 新 Light/Standard 默认 hybrid；Strict 只有项目适配层明确允许才启用自助派发。

### 5.2 回滚

- 新 Run 改用 `dispatch_policy=central`、`execution_profile=normal`，不需要改事件历史。
- 停止使用 `agent_dispatch.py`/`agent_claim.py`；原有 Coordinator 和 Protocol v3 继续运行。
- 只有兼容性测试失败时才从 Skill `1.4.0` 回退到 `1.3.0`；Protocol v3 和项目交付版本不变。
- 不删除 Claim、operation、result、evidence；通过不可变事件把 Run 标记为 blocked/superseded 并归档。
- 回滚不能授予 Release 权限，也不能隐藏失败的自助尝试。

## 6. 风险和防护

| 风险 | 防护 | 失败时的处理 |
| --- | --- | --- |
| 自助发布扩大范围 | 父任务 hash、Scope Freeze 子集检查、发布锁、不可变 causation | 写入前拒绝 |
| 两个 Agent 抢同一任务/线程 | 排他 Claim 锁、一个 active Claim、不可变 lease | 返回冲突，不产生第二 Owner |
| Publisher 自审 | Preflight 检查 Owner 与 Reviewer/QA 身份和能力 | `TASK_READY` 拒绝 |
| Native 成功但任务未执行 | operation、invocation、ACK/result 三重证据 | 只保留 `message_sent` |
| 重试造成外部副作用重复 | 必须声明 side-effect；Strict unknown 不重试 | BLOCKED，等待人工恢复 |
| fast 被误解为降低安全 | 风险取最高等级，不能降级 | Preflight/validator 拒绝 |
| Agent 数量膨胀 | 能力挂在既有 Agent 上，不创建 Dispatcher | 未注册目标直接拒绝 |
| DPXX 规则泄露到通用 Skill | 项目引用保持 opaque，环境枚举由 adapter 提供 | 通用 Skill 不写 MG/成都 |
| 旧 Run 断裂 | 可选字段、central/normal 默认、增量迁移 | 旧 v3 必须继续通过 |
| Candidate 被误认为发布成功 | 权限状态只做观察，Release 由 adapter 决定 | 不写 `RELEASE_READY` |

## 7. 最终完成定义

只有同时满足以下条件才算完成：

- Skill 为 `1.4.0`，Protocol 仍为 v3，README/SKILL/CHANGELOG/OpenAI metadata/静态 Agent 目录一致。
- Light/fast 有真实的单 Agent 路径，不要求 version/release/Review/QA 证据。
- Standard/fast 只有一个独立合并质量交接，且一次报告所有缺口。
- Strict 仍 fail-closed，无自动降级或生产动作。
- `preflight_run.py`、`completion_preflight.py` 默认只读、JSON 输出、可重复、已测试。
- timeout recovery 有界、不可变、考虑 side-effect，不伪造失败或完成。
- 授权工作 Agent 能在不唤醒主 Coordinator 的情况下发布子任务，且有串行、范围、审计保证。
- 任务和 Native 线程 Claim 是首个有效者获胜，不能产生两个 active owner，也不能静默接管。
- 没有资源 lease 时，resource-free 步骤可以继续；resource-required 步骤按 FIFO 等待。
- Native 和 Document adapter 使用同一 task/claim/hash/workspace 事实，fallback 明确可查。
- Candidate 摘要可被项目 Release-Ops 消费，但不会授予发布权限。
- 旧 v3 central Run 验证不变，Python 全量测试通过。
